# Decisions

Lightweight decision log for the modernization effort. Detailed upstream/upgrade ADRs live in `docs/adr/` (see `0001-source-distributed-agent-upgrades.md`) — this file is for redesign-scoped decisions only. Do not reverse an entry here without a technical reason recorded alongside it.

| Decision | Why | Reversal condition |
|---|---|---|
| Vendure ActiveOrder remains the sole cart source of truth | Avoids divergence between a local/optimistic cart and server state; prior incidents (`ORDER_MODIFICATION_ERROR` races) already required a retry workaround (`withCartModificationRetry`) — a second cart state would compound this | Only if Vendure adds a supported client-side cart cache API |
| Full static export (`output: 'export'`) — supersedes the earlier "SSR preserved for dynamic routes" / "static+ISR via partialPrefetching" entries below, which described an interim state (2026-09-02) | Superseded by a later request to remove the server entirely (S3+CloudFront hosting, no Node runtime). Cart/checkout/auth/currency were re-architected around this: ActiveOrder calls happen client-side against Vendure directly (`platform/vendure/client-api`), the currency cookie is read/written client-side (`features/currency/currency.ts`), and there is no middleware, Server Action, or `cookies()`/`headers()` read anywhere in `src/` — verified by repo-wide search. `cacheComponents`/`partialPrefetching` (ISR-oriented PPR) were meaningless without a server and were removed in this migration | Only if S3+CloudFront static hosting is abandoned for a platform with a Node runtime |
| Product/collection detail content prerendered via `generateStaticParams`, enumerating every slug (product/collection) at build — no fallback | Static export has no on-demand rendering for a slug that wasn't prerendered at build, unlike the interim ISR approach | Only if build time/storage from prerendering the full catalog becomes a problem — would need a different hosting model with on-demand rendering |
| Product/collection listings render a real, build-time-fetched default price/stock or product list, then upgrade to a live client fetch (2026-09-03) | Rendering nothing until a client-side `useEffect` resolves (the original static-export approach, on the reasoning that price/stock/listing are currency- and query-string-dependent so must never be "baked in") left product price and, on collection pages, the entire product grid absent from the statically-exported HTML — a real SEO regression, since crawlers don't execute the post-mount fetch. The fix bakes in the real value already fetched server-side at build (channel default currency, no filters/page 1) as the initial render, then a live client fetch (correct for the viewer's active currency, or any filter/sort/page the URL specifies) supersedes it — see `product-price-client.tsx`, `product-info.tsx`, `collection-results.tsx` | Only if build-time price stability becomes unacceptable (e.g. prices change intra-day) — would need on-demand rendering instead of static export |
| Any reactive UI (filters, sort, pagination, variant selection, "current URL" reads) must not call `next/navigation`'s `useSearchParams()` directly — isolate the one necessary call in `features/search/search-params-sync.tsx` and thread the value down as a plain `searchParamsString` prop (2026-09-03) | Under `output: 'export'`, `useSearchParams()` de-opts its *nearest ancestor Suspense boundary* to client-side-only rendering (there's no per-request server to resolve dynamic search params at build time) — this blanks out the **entire boundary's** static HTML, not just the piece of state that depends on the hook. This was the actual root cause of the reported PDP bug (price missing until a storage option was picked) — `product-info.tsx` called the hook directly, bailing the whole PDP to `BAILOUT_TO_CLIENT_SIDE_RENDERING`, and the same pattern independently existed in `collection-results.tsx`/`facet-filters.tsx`/`sort-dropdown.tsx`/`pagination.tsx`, blanking the entire product grid on collection pages. Fixed by removing every direct `useSearchParams()` call from visible components (initial render state now derives from server-provided defaults, e.g. `product.variants[0]`, and same-page URL updates read `window.location.search` post-mount) and centralizing the one required read in `SearchParamsSync`, an invisible component wrapped in its own local Suspense boundary — confining the CSR bailout to something that renders nothing anyway. Verified by inspecting the exported HTML directly (`out/en/product/tablet/index.html`, `out/en/collection/electronics/index.html`) for the absence of `BAILOUT_TO_CLIENT_SIDE_RENDERING` around visible content and the presence of real prices/product cards | Only if `useSearchParams()` gains static-export support without a Suspense-boundary cost, or the app moves off full static export |
| Each product variant gets its own prerendered static page — `/product/[slug]/[[...variant]]`, the optional segment being the variant's SKU — instead of a single page whose variant selector only updates client-side state (2026-09-03) | Even after the `useSearchParams()` fix above, selecting a non-default variant (e.g. a different storage size) was still a purely client-side DOM update with no corresponding URL/page — so a fresh page load or "View Page Source" of that same URL always showed only the default variant's price, never the one just selected; this is fundamentally different from the `useSearchParams` bug and can't be fixed by adjusting Suspense boundaries; the only way a specific variant's data can appear in a static HTML response is for that variant to have its own prerendered page. `generateStaticParams` (`getProductVariantParams` in `features/products/data.ts`) now enumerates every non-default variant per product (by SKU) in addition to each product's own slugs; the default variant (`product.variants[0]`) keeps the bare `/product/[slug]` URL, matching all existing links (product cards, collections, breadcrumbs). Selecting an option in `product-info.tsx` now looks up the matching variant and does a real `router.push` to its dedicated page rather than updating a query param — so both the live DOM and a plain `view-source`/crawler fetch of that URL show the correct price. Variant sub-pages canonicalize back to the bare product URL (same name/description, only price/stock differ) to avoid diluting ranking signals across near-duplicate pages. A latent, pre-existing data issue surfaced while building this: 2 products return an empty `slug` in the `hi` locale (untranslated) — `getPopularProductSlugs` now filters those out instead of enumerating a bogus `/product//` route or crashing the new per-variant detail fetch | Only if variant count per product grows large enough that prerendering all of them becomes a build-time/storage problem — would need on-demand rendering instead of static export, or capping which variants get their own page |
| `Link` prefetch defaults to `false` app-wide (2026-09-03) | Next.js 16's default `Link` prefetch (the client "segment cache") requests per-route-segment RSC payload files (`__PAGE__.txt`) whose expected path doesn't match what `output: 'export'` actually writes to disk — a confirmed, currently-open upstream bug (vercel/next.js#85374, #92341) that fires a 404 for essentially every rendered link (product cards, collections, cart, search, nav, home), not just one route family. It's cosmetic — a failed prefetch falls back to a normal full navigation, real clicks/`router.push` to prerendered pages still work — but it's console/network noise on every page. Rather than passing `prefetch={false}` at each of the ~40 call sites, the fix is centralized at the two places nearly everything routes through: `platform/i18n/navigation.tsx`'s `Link` (wraps next-intl's `Link`, used by all client components) and `site/navigation/navigation-link.tsx`'s `NavigationLink` (wraps `next/link` directly, used by cached server components) both now default `prefetch` to `false` unless a caller explicitly opts back in. Verified: `check-types`/`lint`/`build` pass, static export still serves `/`, `/product/[slug]`, `/product/[slug]/[sku]`, `/collection/[slug]`, `/cart`, `/search` at 200 with real baked-in prices intact | Revert once Next ships a fix for #85374 under `output: 'export'` — re-enable default prefetch by removing the `prefetch = false` default in both wrappers |
| Live client-side price re-fetch is deduped and skipped when the viewer's currency matches the build-time default (2026-09-03) | A product page fired a dozen-plus near-simultaneous `shop-api` POSTs on load: every mounted `ProductCardPrice` (one per related-product card) plus `ProductInfo` independently called `useLiveProductPricing`, and every one of those independently re-resolved `getActiveCurrencyCode()` → `getActiveChannel()` with no caching (`channel-client.ts`'s own comment admitted this). Fixed by (1) memoizing `getActiveChannel()` in a module-level singleton promise shared by every caller for the page's lifetime (`platform/vendure/channel-client.ts`), and (2) having `useLiveProductPricing` skip its `GetProductDetailQuery` re-fetch entirely once the resolved currency equals the `buildCurrencyCode`/`initial.currencyCode` already baked in at build time — the build-time price is provably correct in that case, so there's nothing to gain by re-fetching it. For the common case (viewer browsing in the channel's default currency), this takes a PDP's live-fetch network calls to zero after the one shared channel check; only a genuinely different active currency triggers real per-product re-fetches. Verified: static export still bakes in real prices with no `useSearchParams`-style bailout (`out/en/product/tablet/index.html` → ₹394.80, `.../TBL200128/index.html` → ₹534.00); `check-types`/`lint`/`test`/`build` all pass with no new failures | Only if per-product live data (e.g. real-time stock, not just currency) becomes required even when currency matches — would need the skip condition narrowed or removed |
| `npm start` serves the static export (`serve out`) instead of `next start` (2026-09-03) | `next start` requires a Node server and throws `Error: "next start" does not work with "output: export" configuration` — a bug introduced when the app moved to full static export but the script was never updated. `npm run dev` (`next dev`) is still the right tool for iterating on UI, but it runs a per-request dev server and does **not** reproduce static-export-only behavior (per-variant static pages, `useSearchParams()` CSR bailout confinement, baked-in build-time prices) — verifying those requires the actual exported `out/` HTML. `npm start` now runs `npx serve@latest out -l 3001` directly (assumes `out/` already built); `npm run serve` still does `build && start` in one step for a from-scratch check | Only if the app gains a Node runtime again (moves off `output: 'export'`) |
| No new state-management library | Existing architecture (ActiveOrder for cart, URL params for filters, local component state for UI) already covers all state categories needed for the redesign | Only if a cross-cutting UI state emerges that URL/local state can't express |
| Reuse existing shadcn primitives (`src/components/ui/*`) before adding dependencies | Broad primitive set already scaffolded (drawer, sheet, carousel, command, etc.); adding new libraries risks bundle size and SSR compatibility | Only if a primitive is structurally missing (e.g. no image-zoom/lightbox primitive exists yet) |
| Currency resolution stays server-validated (`getActiveCurrencyCode`) | Fixed 2026-08-29 bug where stale `vendure-currency` cookie leaked USD after channel was reconfigured to INR-only; validation against `channel.availableCurrencyCodes` is the guard | N/A — regression would reopen the original bug |
| Stripe settlement stays webhook-driven (async) | `placeOrder`/`addPaymentToOrder` intentionally not called for Stripe; order confirmation polls/waits via `PaymentProcessingBanner` until `orderPlacedAt` is set post-webhook | Only if Stripe integration architecture changes (out of scope for UI redesign) |
| Atta Chakki catalog focus via `config/catalog-focus.ts` — scope listings to a Vendure collection rather than delete or unpublish products (2026-10-08) | Client direction: the site must read as an Atta Chakki brand, but nothing may be deleted. Scoping with Vendure's own `SearchInput.collectionSlugs` keeps pagination, counts and facet OR/AND semantics correct (a client-side filter after fetch would not), and keeps every product page prerendered so old links, orders and account history keep working. The focus collection is named by slug in one config file (like `config/pricing.ts` by SKU) because the client-side listings need it without a build-time prop chain; if the slug disappears, `getShopCategories` falls back to all categories but listings would be empty, so keep it in step with the admin. Removed UI is commented out in place ("Hidden 2026-10-08") instead of deleted, per the client | Client asks for the full catalogue again → set `FOCUS_COLLECTION_SLUGS` to `[]` and uncomment the hidden homepage sections / nav items |
| Millnex machine catalog lives in the site layer (`site/catalog/machines.ts`), not Vendure (2026-09-28) | The Millnex channel has zero products (only two empty collections), and Vendure's default product model has no fields for motor power, capacity, dimensions or grinding materials. The showcase and `/machines/[slug]` pages therefore read a typed module transcribed from the published millnex.in product pages (`sourceUrl` per entry) — nothing invented; where millnex.in contradicts itself the spec table wins and the conflict is commented inline. No prices are shown (none are published): cards say "Get Latest Price" and open the enquiry form. The Vendure PDP/PLP routes are untouched and keep working for any product added later | Once Millnex products exist in Vendure with spec custom fields (motor, capacity, dimensions, weight, materials), switch the showcase/detail pages to Vendure data and delete the catalog module |
| Marketing copy is English brand content in `site/content/*`; only UI chrome goes through next-intl (2026-09-28) | The channel's only language is `en`, and the copy is brand/catalog content analogous to Vendure product text (which the storefront doesn't translate either). Buttons, navigation, form labels/validation, breadcrumbs and page metadata are translated for all four routed locales so shared chrome (also used by cart/checkout/account) stays localized | If Millnex adds non-English channel languages — move the copy into message files per locale |
| Enquiries are delivered client-side: `NEXT_PUBLIC_ENQUIRY_ENDPOINT` JSON POST → WhatsApp hand-off → mailto hand-off (2026-09-28) | The storefront is a static export with no server, and neither Vendure's Shop API nor the repo had any contact/enquiry mechanism, so there was no existing backend to connect to. A configurable endpoint (form service, serverless function, CRM webhook) is the only server-side option that keeps hosting static; hand-offs keep the form useful before one is configured. With nothing configured the form shows an explicit "not available yet" error rather than pretending to send | If a first-party enquiry API is added (e.g. a Vendure plugin mutation), submit through it instead |
| `next-themes` provider unmounted; brand is light-first (2026-09-28) | The design system pairs light surfaces with fixed dark "ink" sections rather than a user dark mode, and the provider's inline theme script triggered React's "Encountered a script tag while rendering React component" console error on every client render. The `.dark` tokens and `theme-switcher.tsx` are kept, unmounted | Remount `site/providers/theme-provider.tsx` (and the switcher) if a dark mode is designed for the new brand |
| Empty catalog keeps the static export building via a `__empty__` placeholder param (2026-09-28) | `output: 'export'` fails the entire build when a dynamic route's `generateStaticParams()` returns `[]`, which is exactly what `product/[slug]` (and `collection/[slug]`) return for a channel with no catalog — the build was already failing before the redesign. `platform/next/static-export.ts` substitutes one sentinel param; both pages `notFound()` for it, so only an unlinked 404 page is exported | Remove once the channel always has catalog content, or if Next.js allows empty `generateStaticParams` under static export |
| `app/` shims may declare literal `export const dynamic`/`revalidate` (2026-09-28) | `sitemap.ts`/`robots.ts` must be `force-static` under `output: 'export'`, and Next.js rejects route segment config that is re-exported from another module ("It mustn't be reexported"). The architecture test now allows a literal-valued `dynamic`/`revalidate` export alongside the re-export; everything else in `app/` must still be a re-export | If Next.js starts reading re-exported segment config |
| Wishlist is device-local: Vendure product IDs in `localStorage` (`features/products/wishlist.ts`), re-read from Vendure on display (2026-09-28) | The Vendure Shop API has no wishlist entity or mutation, and adding a Vendure plugin is out of scope for a presentation redesign. Only IDs are stored — name, image, price and stock always come from Vendure (`GetWishlistProductsQuery`), and IDs Vendure no longer returns are pruned. It is not a cart and never touches the ActiveOrder. The page says "saved on this device" so it doesn't pretend to sync across devices/accounts | If a wishlist plugin (customer-scoped) is added to Vendure — move storage to it and keep the device list as the signed-out fallback |
| Shop sort defaults to "Featured" (no `sort` sent, Vendure's own ranking) and adds a real category filter (`?category=` → `SearchInput.collectionSlugs`); no price filter or Newest sort (2026-09-28) | Requested ecommerce sort/filter set was Featured / Newest / Price, and Categories / Price / Motor Power / Availability. The Shop API's `SearchInput` has no price range and `SearchResultSortParameter` only name/price, so a price filter or newest sort could only be faked client-side over one page of results (wrong counts, wrong pagination). Motor power works as any Vendure facet. Facet OR/AND semantics are unchanged | If the Elasticsearch plugin (priceRange) or a custom search sort is enabled on the server |
| Removed the hardcoded site-layer machine catalog; every product surface reads Vendure (2026-09-28) — supersedes "Millnex machine catalog lives in the site layer" above | Requirement: no manually maintained frontend catalogue — a product added in Vendure admin must appear without code changes. `/machines` is now a noindex client redirect to `/shop`. The channel currently has 0 products, so product sections render their empty states | N/A |
| PDP URL stays `/product/<slug>` rather than the requested `/products/<slug>` (2026-09-28) | Every variant has its own prerendered `/product/<slug>/<sku>/` page, sitemap and canonical URLs are built on it, and static export has no server rewrites — renaming means duplicating or client-redirecting every product page for a cosmetic change | If URL naming becomes an SEO/marketing requirement — rename the route folder and add `site/legacy`-style redirects |
| Graphite "ink" sections are back: home hero + trust strip, spotlight, manufacturing, About/Manufacturing heroes, quote modal side panel and the footer (2026-09-29) — reverses "fully light since 2026-09-28" | The 2026-09-29 client redesign brief asks for a premium industrial identity with deep charcoal/graphite as the primary colour, strong contrast and strong section transitions; an all-light site read as "template".
